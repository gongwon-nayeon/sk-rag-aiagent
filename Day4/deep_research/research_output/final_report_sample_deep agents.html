Executive Summary

LangChain Deep Agents는 단순한 챗봇 프레임워크가 아니라, 긴 시간 동안 여러 도구를 호출하고 중간 산출물을 관리해야 하는 작업을 위해 만들어진 배터리 포함형 에이전트 하네스(agent harness)다. LangChain 공식 문서는 Deep Agents를 파일시스템, 하위 에이전트, 장기 메모리, 컨텍스트 관리, human-in-the-loop 등을 기본 제공하는 장기 작업용 에이전트 구축 도구로 설명한다[1].

핵심 질문은 “Deep Agents가 기존 LangChain 에이전트나 LangGraph와 무엇이 다르고, 실제로 언제 써야 하는가”다. 결론부터 말하면, 간단한 질의응답이나 단일 API 호출에는 과하지만, 리서치·코딩·문서 작성·데이터 분석·업무 자동화처럼 긴 실행, 파일 기반 중간 결과, 사람 승인, 하위 작업 분리가 필요한 경우에는 강력한 선택지다[1][3][6]. 다만 기본적으로 LLM이 도구를 호출하는 구조이므로, 보안 경계는 모델이 아니라 도구 권한·샌드박스·승인 정책·관측성에서 만들어야 한다[6][8].

Key Findings

  • Deep Agents는 LangGraph 위에 올라간 고수준 하네스다. LangGraph의 durable execution, streaming, persistence, human-in-the-loop 같은 실행 능력을 활용하면서, 파일시스템·subagents·memory·skills·summarization을 미리 조립해 제공한다[1][6].
  • 초기 LangChain 블로그는 성공적인 “deep agent”의 공통 패턴을 상세한 시스템 프롬프트, planning tool, subagents, file system 네 가지로 정리했다[2]. 현재 Deep Agents는 이 패턴을 공식 SDK 형태로 제품화한 것으로 볼 수 있다[1][6].
  • 현재 공식 API의 핵심 함수는 create_deep_agent이며, 인자명은 instructions가 아니라 system_prompt다. 주요 인자로 model, tools, middleware, subagents, skills, memory, permissions, backend, interrupt_on, checkpointer, store, cache 등이 지원된다[4].
  • Planning/todo는 현재 기본값이 아니라 opt-in이다. v0.7부터는 TodoListMiddleware()를 명시적으로 추가해야 write_todos 계획 도구를 사용할 수 있다[1][3].
  • GitHub Releases 기준 Deep Agents SDK 최신 릴리스는 deepagents==0.7.23이며, 2026년 10월 7일 릴리스로 표시된다. 별도 터미널 코딩 에이전트 패키지인 deepagents-code와는 구분해야 한다[7].

1. Deep Agents의 정체와 등장 배경

Deep Agents를 이해하려면 먼저 “에이전트 루프”와 “긴 작업을 완수하는 실행 환경”을 구분해야 한다. 기본적인 LLM 에이전트는 모델이 메시지를 읽고, 필요한 도구를 호출하고, 도구 결과를 다시 보고 다음 행동을 결정하는 반복 구조다. 이 구조만으로도 간단한 검색, 계산, API 호출은 가능하지만, 수십 단계에 걸친 조사나 코드 수정처럼 중간 산출물이 많고 실패 가능성이 높은 작업에서는 쉽게 얕아진다[2].

LangChain 창업자 Harrison Chase는 2025년 7월 30일 글에서 OpenAI Deep Research, Manus, Claude Code 같은 장기 작업형 에이전트의 공통점을 분석하며, 단순한 도구 호출 루프만으로는 “deep”한 결과를 만들기 어렵다고 설명했다. 그가 제시한 공통 패턴은 상세한 시스템 프롬프트, planning tool, subagents, file system이다[2]. Deep Agents는 이 네 가지 패턴을 LangChain/LangGraph 생태계에서 바로 쓸 수 있도록 묶은 오픈소스 패키지다[1][6].

따라서 Deep Agents는 LangChain의 create_agent를 대체하는 단순 래퍼라기보다, 장기 실행에 필요한 운영 장치를 포함한 상위 레이어다. LangChain은 모델·도구·메시지·미들웨어 같은 구성 요소를 제공하고, LangGraph는 상태 기반 실행, 체크포인팅, 스트리밍, interrupt를 맡는다. Deep Agents는 그 위에서 파일시스템, 하위 에이전트, 메모리, 스킬, 요약, 승인 흐름을 기본 조합으로 제공한다[1][4][6].

2. 핵심 구조: 장기 작업을 위한 네 가지 실행 장치

앞서 본 등장 배경이 “단순 루프의 한계”라면, Deep Agents의 실제 차별점은 그 한계를 보완하는 실행 장치를 기본 제공한다는 데 있다. 특히 파일시스템, 하위 에이전트, 계획 도구, 승인·권한 제어가 핵심이다.

파일시스템: 컨텍스트 창 밖의 작업 메모리

Deep Agents는 가상 파일시스템(virtual filesystem)을 제공한다. 에이전트는 ls, read_file, write_file, edit_file, delete, glob, grep 같은 파일 도구를 사용해 중간 결과를 저장하고 다시 읽을 수 있다. 샌드박스 백엔드를 사용할 때는 execute를 통해 셸 명령 실행도 가능하다[1][5].

이 구조의 의미는 크다. 긴 리서치나 코딩 작업에서는 모든 검색 결과, 코드 조각, 초안, 오류 로그를 대화 컨텍스트에 계속 넣을 수 없다. Deep Agents는 큰 도구 결과를 파일로 오프로드하고, 필요할 때 부분적으로 다시 읽는 방식으로 컨텍스트 압박을 줄인다[1]. read_file은 offset/limit 방식의 부분 읽기를 지원하며, 공식 문서는 멀티모달 파일 처리도 언급한다[1].

Subagents: 하위 작업을 격리된 컨텍스트로 분리

Deep Agents에는 기본적으로 task 도구가 포함되며, 이를 통해 임시 하위 에이전트(ephemeral subagent)를 만들 수 있다. 하위 에이전트는 매번 새로운 컨텍스트에서 독립적으로 실행되고, 최종 결과만 상위 에이전트에 반환한다[1].

이 방식은 긴 작업의 토큰 사용량과 복잡도를 줄이는 데 유용하다. 예를 들어 경쟁사 5곳을 조사해야 할 때 상위 에이전트가 모든 검색 결과를 직접 안고 가는 대신, 하위 에이전트들이 각 회사를 조사한 뒤 요약 결과만 반환하게 할 수 있다. 공식 문서에 따르면 기본 general-purpose subagent가 활성화되어 있고, subagents= 인자로 역할별 custom subagent도 정의할 수 있다[1][4].

Planning/todo: 현재는 opt-in 기능

초기 Deep Agents 논의에서 planning tool은 중요한 요소였지만, 현재 공식 문서 기준으로는 기본 기능이 아니라 opt-in이다. v0.7부터 task planning은 기본 미들웨어에서 빠졌고, write_todos 도구를 쓰려면 TodoListMiddleware()를 명시적으로 추가해야 한다[1][3].

from deepagents import create_deep_agent
from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(
    model="anthropic:claude-sonnet-5",
    middleware=[TodoListMiddleware()],
)

계획 도구는 복잡한 작업에서 “해야 할 일”, “진행 중인 일”, “완료된 일”을 상태로 남기게 해 준다. 단, 모든 작업에 필요한 것은 아니다. 간단한 질의응답에서는 오히려 호출 비용과 지연만 늘릴 수 있다[1].

Human-in-the-loop과 권한 제어

Deep Agents는 LangGraph interrupt 기반의 human-in-the-loop을 지원한다. 예를 들어 interrupt_on={"edit_file": True}를 설정하면 파일 편집 도구가 실행되기 전에 그래프가 멈추고, 사용자가 승인·수정·거절 같은 결정을 내릴 수 있다[1][4][8].

파일 권한은 permissions=로 제어한다. 규칙은 operations, paths, mode를 포함하며, allow, deny, interrupt 같은 모드를 사용할 수 있다[1][4]. 이 기능은 .env, credential, 고객 데이터, 운영 DB 변경 도구처럼 민감한 대상에 접근할 때 필수적이다.

구성요소 역할 실무적 의미
Virtual filesystem 중간 산출물 저장·검색·수정 긴 리서치, 코드 수정, 보고서 초안 관리에 유리
Subagents 하위 작업을 독립 컨텍스트로 위임 토큰 폭증 완화, 역할별 분업 가능
Todo middleware 계획과 진행 상태 관리 복잡한 multi-step task에서 유용하나 v0.7부터 opt-in
Human-in-the-loop 위험 도구 실행 전 승인 파일 수정, 삭제, 외부 발송, DB 변경에 필요
Permissions 파일 경로·작업별 접근 제어 LLM이 아닌 도구 계층에서 보안 경계 설정

3. 설치와 기본 사용법: create_deep_agent 중심 API

Deep Agents의 사용법은 create_deep_agent를 중심으로 단순하게 시작한다. 공식 Quickstart는 pip install deepagents 또는 uv add deepagents를 안내하며, GitHub README도 uv add deepagents를 빠른 시작 설치 명령으로 제시한다[3][6].

pip install deepagents
# 또는
uv add deepagents

가장 작은 형태의 예제는 도구 함수와 시스템 프롬프트를 넘겨 에이전트를 만드는 방식이다. 공식 Overview는 날씨 조회 도구를 예로 들어 create_deep_agent(model=..., tools=[...], system_prompt=...) 형태를 보여준다[1].

from deepagents import create_deep_agent

def get_weather(city: str) -> str:
    """Get weather for a given city."""
    return f"It's always sunny in {city}!"

agent = create_deep_agent(
    model="openai:gpt-5.5",
    tools=[get_weather],
    system_prompt="You are a helpful assistant",
)

agent.invoke({
    "messages": [{"role": "user", "content": "what is the weather in sf"}]
})

공식 문서와 README에는 openai:gpt-5.5, openai:gpt-6-astra 같은 미래형으로 보이는 모델명이 실제 예시로 등장한다[1][3][6]. 다만 이는 “문서 예시에 포함되어 있다”는 뜻이지, 모든 환경에서 해당 모델명이 실제 공급자 API로 호출 가능하다는 보증은 아니다.

현재 공식 Customization 문서 기준 create_deep_agent의 주요 인자는 다음과 같다[4].

인자 의미
model provider 문자열 또는 LangChain chat model 객체
tools 사용자 정의 함수, LangChain tool, MCP 도구 등 추가 도구
system_prompt 에이전트의 사용자 지정 시스템 지시문
middleware Todo, guardrail, custom middleware 등 추가 미들웨어
subagents custom subagent 정의 목록
skills 전문 워크플로와 도메인 지식을 담은 skill 소스
memory AGENTS.md 기반 장기 지침·프로젝트 규칙
permissions 파일 작업별 allow/deny/interrupt 규칙
backend state, local disk, LangGraph store, sandbox 등 파일 백엔드
interrupt_on 특정 도구 호출 전 human-in-the-loop interrupt 설정
checkpointer, store, cache LangGraph 계층의 상태 저장, 장기 저장, 캐시
state_schema, context_schema 상태와 런타임 컨텍스트 스키마 확장

중요한 점은 현재 공식 시그니처의 인자명이 instructions가 아니라 system_prompt라는 것이다[4]. 오래된 예제나 비공식 자료를 볼 때 이 차이를 확인해야 한다.

4. 적합한 활용 영역: 리서치·코딩·업무 자동화

Deep Agents가 모든 에이전트 문제의 정답은 아니다. 강점은 “길고 복잡하며 중간 산출물이 많은 작업”에서 두드러진다.

빠르게 맞는 영역: Deep research와 문서 작성

공식 Quickstart의 대표 예시는 research agent다. 검색 도구로 정보를 수집하고, 큰 검색 결과는 파일시스템에 저장하며, 필요하면 subagent를 생성해 조사 범위를 나눈 뒤 최종 보고서를 합성하는 흐름이다[3]. 초기 LangChain 블로그도 open_deep_research를 Deep Agents 위에 만든 예시로 언급했다[2].

이 구조는 시장 조사, 기술 조사, 경쟁사 분석, 정책 문서 작성, 제품 기획 문서 작성처럼 “자료 수집 → 정리 → 초안 → 검토” 단계를 거치는 작업에 잘 맞는다. 파일시스템은 노트와 초안 저장소 역할을 하고, subagent는 개별 주제 조사를 맡으며, 상위 에이전트는 최종 종합을 담당할 수 있다[1][3].

강점이 분명한 영역: 코딩 에이전트

코딩 작업은 Deep Agents와 궁합이 좋다. 코드베이스 탐색, 파일 수정, 테스트 실행, 오류 로그 분석, 수정 반복이 모두 필요하기 때문이다. GitHub README는 Deep Agents Code를 Claude Code나 Cursor와 유사한 터미널용 사전 구성 코딩 에이전트로 소개한다[6].

코딩 에이전트에서는 특히 권한과 샌드박스가 중요하다. 테스트 실행이나 빌드 명령은 execute가 필요하지만, 실제 운영 파일이나 비밀값에 접근해서는 안 된다. 따라서 Deep Agents의 파일 권한, sandbox backend, human-in-the-loop을 함께 설계해야 한다[1][5][8].

신중히 접근할 영역: 운영 업무 자동화와 외부 시스템 변경

고객지원 티켓 처리, CRM 업데이트, 이메일 초안 작성, 내부 지식 검색, 데이터 분석 자동화도 Deep Agents의 후보 영역이다. MCP를 통해 외부 API, 데이터베이스, SaaS 도구를 연결할 수 있고, tools=에 일반 함수나 MCP 서버 도구를 넘길 수 있다[5].

다만 실제 운영 시스템을 변경하는 도구는 위험도가 높다. 이메일 발송, 결제 처리, DB write, 파일 삭제 같은 작업은 자동 실행보다 interrupt_on이나 permissions의 interrupt 모드를 통해 승인 단계를 넣는 편이 안전하다[1][4][8].

5. LangGraph와의 관계: 고수준 하네스와 저수준 런타임의 결합

Deep Agents는 LangGraph와 경쟁하는 것이 아니라, LangGraph 위에서 작동하는 고수준 하네스다. 공식 Overview와 GitHub README는 Deep Agents가 LangGraph 기반의 durable execution, streaming, persistence, checkpointing을 활용한다고 설명한다[1][6].

이 관계는 다음처럼 정리할 수 있다.

계층 역할 Deep Agents와의 관계
LangChain 모델, 도구, 메시지, 미들웨어 구성 요소 Deep Agents의 도구·모델·미들웨어 기반 제공
LangGraph 상태 기반 그래프 런타임, 체크포인팅, interrupt Deep Agents의 실행·영속성·재개 기능 담당
Deep Agents 파일시스템, subagents, memory, skills, permissions가 포함된 하네스 장기 작업용 기본 조립 세트 제공

Deep Agents의 checkpointer, store, state_schema, context_schema, cache 같은 인자는 LangGraph 계층과 직접 연결된다[4]. Human-in-the-loop도 LangGraph interrupt와 persistence layer에 의존한다. interrupt가 발생하면 상태가 저장되고, 같은 thread context에서 승인 후 재개할 수 있다[8].

따라서 프로세스를 아주 세밀하게 직접 설계해야 한다면 LangGraph를 직접 쓰는 편이 낫다. 반대로 “파일시스템, 하위 에이전트, 메모리, 승인 흐름이 이미 들어간 장기 작업 에이전트”가 필요하다면 Deep Agents가 출발점으로 더 빠르다[1][6].

6. 경쟁 프레임워크와 비교: Deep Agents가 강한 지점

Deep Agents는 멀티에이전트 프레임워크라기보다 “장기 작업을 완수하는 단일/다중 에이전트 실행 하네스”에 가깝다. 이 관점에서 경쟁·관련 프레임워크와 차이를 봐야 한다.

프레임워크 강점 Deep Agents와의 차이
LangGraph 그래프 단위의 세밀한 상태·흐름 제어 Deep Agents는 LangGraph 위에 미리 조립된 고수준 하네스[1][6]
LangChain create_agent 가벼운 기본 에이전트 생성 Deep Agents는 파일시스템·subagents·memory·permissions가 더 전면에 있음[4]
Claude Agent SDK Claude Code 생태계와 긴밀한 deep agent 환경 Deep Agents는 LangChain 모델 생태계와 LangGraph/LangSmith 통합을 중시[9]
OpenAI Agents SDK handoff, guardrails, tracing 등 OpenAI 중심 primitive Deep Agents는 파일 기반 컨텍스트 관리와 하위 에이전트 격리가 강점[1][5]
CrewAI 역할 기반 multi-agent crew 구성 Deep Agents의 subagent는 협업 조직보다 컨텍스트 격리·하위 작업 위임에 가까움[1][4]
AutoGen 계열 대화형 multi-agent orchestration Deep Agents는 권한, 파일시스템, 체크포인팅, HITL을 묶은 장기 실행 하네스 성격이 강함[1][8]
AutoGPT류 높은 자율 실행과 반복 루프 Deep Agents는 무제한 자율성보다 통제 가능한 도구 권한과 관측성을 중시[6][8]

공식 비교 문서는 Deep Agents가 OpenSWE와 LangSmith Fleet 같은 프로덕션 시스템에 쓰였다고 밝히며, Claude Agent SDK와 비교해 모델·배포·운영 선택지가 더 넓다는 점을 강조한다[9]. 다만 공개 문서상 특정 벤치마크 성공률이나 ROI 수치는 제한적이므로, 실제 도입 시에는 조직의 작업 유형별로 자체 평가를 설계해야 한다.

7. 도입 시 주의점: 권한·비용·평가 체계를 먼저 설계해야 한다

Deep Agents의 장점은 곧 리스크이기도 하다. 파일을 읽고 쓰고, 셸을 실행하고, 외부 API를 호출하고, 하위 에이전트를 만들 수 있다는 것은 강력하지만, 잘못 구성하면 비용·보안·품질 문제가 빠르게 커진다.

첫째, 도구 권한이 곧 보안 경계다. GitHub README는 Deep Agents가 기본적으로 LLM을 신뢰하는 실행 모델을 따른다고 설명한다. 즉 에이전트는 도구가 허용한 일을 할 수 있으므로, 안전성은 모델의 선의가 아니라 도구 allowlist, 파일 권한, 샌드박스, 승인 정책에서 확보해야 한다[6].

둘째, 프롬프트 인젝션 위험이 크다. Research agent나 코딩 에이전트는 웹 페이지, 문서, README, 이슈, 이메일처럼 신뢰할 수 없는 입력을 읽는다. 외부 문서 안의 악성 지시가 도구 호출로 이어질 수 있으므로, 민감 도구는 read-only로 시작하고, write·delete·send·execute 계열 작업에는 interrupt를 적용하는 것이 바람직하다[1][5][8].

셋째, 비용과 지연이 늘 수 있다. Deep Agents는 subagent 호출, 파일 읽기·쓰기, 검색, 요약, human approval 등 여러 단계를 포함할 수 있다. 단순 create_agent보다 더 많은 모델 호출과 도구 호출이 발생할 가능성이 높다[1][3]. 긴 리서치 작업에서는 검색 API 비용과 토큰 비용도 함께 관리해야 한다.

넷째, 관측성과 평가가 없으면 운영하기 어렵다. 장기 에이전트는 실패 원인이 모델 판단, 도구 오류, 권한 설정, 파일 상태, 하위 에이전트 결과 중 어디에 있는지 파악하기 어렵다. 공식 문서와 README는 LangSmith를 통한 trace, debug, evaluation, monitoring을 권장한다[1][6].

리스크 발생 상황 권장 대응
민감 파일 노출 .env, credential, 고객 데이터 접근 permissions로 deny/interrupt 규칙 설정
파괴적 변경 파일 삭제, 코드 대량 수정, DB write interrupt_on, human approval, sandbox 적용
프롬프트 인젝션 웹·문서·이메일을 읽는 에이전트 도구 allowlist, read-only 기본값, 출력 검증
비용 폭증 subagent·검색·요약 반복 호출 한도, 작업별 budget, observability 설정
디버깅 난이도 긴 실행 중 실패 LangSmith trace, checkpoint, 테스트셋 평가

8. 최신 상태와 실무적 결론

Deep Agents는 2025년 7월 30일 LangChain 블로그에서 본격 소개된 뒤 SDK와 공식 문서가 빠르게 확장됐다[2]. 현재 공식 문서는 /oss/python/deepagents/... 경로에서 Quickstart, Overview, Customization, Tools 등을 제공하며, SDK 자체는 아직 1.0이 아닌 0.x 계열이다[1][3][4][5]. GitHub Releases 기준 최신 SDK 릴리스는 deepagents==0.7.23이고, 2026년 10월 7일 릴리스로 표시된다[7].

블로그 소개일 2025.07.30
SDK 계열 0.x
최신 릴리스 0.7.23
릴리스 표시일 2026.10.07

실무적으로는 다음 기준으로 판단하는 것이 좋다.

  • 단순 챗봇, 짧은 Q&A, 한두 번의 API 호출이면 Deep Agents는 과할 수 있다.
  • 파일 기반 작업공간, 여러 단계의 계획, 하위 작업 위임, 중간 산출물 관리가 필요하면 Deep Agents가 적합하다.
  • 코드 수정, 장기 리서치, 문서 생성, 데이터 분석, 내부 업무 자동화처럼 “완성물”이 필요한 작업에서 특히 유리하다.
  • 운영 환경에서는 처음부터 permissions, interrupt_on, sandbox, checkpointer, LangSmith 관측성을 함께 설계해야 한다.

결론적으로 Deep Agents는 “더 똑똑한 단일 프롬프트”가 아니라, 장기 작업을 끝까지 밀고 가기 위한 실행 환경이다. 성공적인 도입의 핵심은 모델 선택보다 작업공간, 권한, 하위 작업 분리, 평가 체계를 어떻게 설계하느냐에 있다. Deep Agents는 이 구조를 LangChain/LangGraph 생태계 안에서 빠르게 시작하게 해 주지만, 운영 안정성은 여전히 사용자가 정의한 도구 경계와 승인 흐름에 달려 있다.
